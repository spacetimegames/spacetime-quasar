= Determinism harness
:description: How to run the cross-platform determinism harness locally and what it checks.

The simulation must be bit-identical on every platform (xref:adr/0008-determinism-implementation.adoc[ADR 0008]).
The harness runs a few small scenarios, takes the state hash every 120 ticks, and compares the result with a committed reference file.
CI runs it on Linux, Windows, macOS and `wasm32-wasip1` (under wasmtime).

Status: minimal simulation, complete comparison.
`st-sim` has a handful of bodies and one command kind, and the harness has five scenarios: three simulation scenarios, `math-kernels` and `data-fixtures` (SPAC-126).
The four producer jobs upload their output, the `determinism` job compares the four files with each other and with the reference, the leak detector runs on x86_64 Linux, and `--dump-tick` writes the canonical hash input for diffing (SPAC-125).

From ADR 0009, these are not built yet: replay files (`st_sim::replay`) and replay scenarios, the command wire encoding with golden bytes and its tag table with the reserved tags, `SIM_VERSION` and its pin file, session commands, the `StepError` variants `NotExternal` and `TickTooLarge`, and the payload (1 MiB) and per-tick (2 MiB) byte limits. The three simulation scenarios are interim and use different names from the scenarios in ADR 0008 (`physics-swarm` and `combat-60s` are not built yet).

Commands tagged `[ci-tested]` are the ones the CI jobs run (CI only differs in the output file name and in providing wasmtime outside the dev shell); run 38130979625 passed the harness, the uploads and the `determinism` compare job on all four targets. Untagged commands were run by an agent inside `nix develop` on the reference dev machine (Linux x86_64).

== What it checks

[cols="1,3",options="header"]
|===
| Scenario | What it runs

| `solo-burn`
| One ship near the origin and one scripted pilot: burn, turn, strafe and brake. 600 ticks (5 s).

| `orbit-coast`
| Eight ships on near-circular orbits whose radii and phases come from `st-rng`. One pilot brakes one ship. 1,200 ticks (10 s).

| `swarm-controls`
| 64 ships 500 km from the origin, one pilot each. The control changes (with gaps in the sequence numbers) come from `st-rng`. 2,400 ticks (20 s).

| `math-kernels`
| No simulation: the `st-math` kernels with fixed inputs. Tick 0 runs a table of 24 edge values (signed zeros, the smallest subnormal, tiny and huge magnitudes, `pi`, angles beyond argument reduction, `f64::MAX`) through every `det` function. Each of ticks 1 to 1,200 (10 s) draws its inputs from `st-rng` and runs every `det` function, the Kepler solver with the element and state-vector conversions and propagation of `orbit` (on valid and on rejected inputs), and `lerp`, `nlerp`, `slerp` and the Hermite curve and velocity of `interp`.

| `data-fixtures`
| No simulation: the four `ship_design` fixture files of `st-data` (versions 1, 2 and 3 and the version-3 file that version 1 migrates to) loaded through the migration chain as one data set. One line, at tick 0: FNV-1a 64 of the 32-byte data-set hash.
|===

The simulation scenarios are in `st_sim::scenarios`, and so is `math-kernels` (`st_sim::scenarios::math_kernels`): ADR 0008 does not say where it lives, and the harness reaches `st-math` and `st-rng` through `st-sim`, as it does for `physics-swarm`.
`data-fixtures` is in the harness crate (`tools/determinism/src/fixtures.rs`), because ADR 0008 makes the harness the user of `st-data` and `st-sim` does not depend on it.
Each simulation scenario has a seed, a setup, a command log (sorted by tick, pilot and sequence number) and a tick count.
The simulation advances only through `Sim::step`, which takes that tick's commands.
Commands name a pilot, and a pilot controls a ship; nothing treats one pilot as the player.

The output has one line per checkpoint: `<scenario> <tick> <hash>`.
The tick is zero-padded to 8 digits and the hash is 16 lower-case hex digits.
Lines are sorted and end with LF.
Checkpoints are tick 0, every 120 ticks (1 s) and the final tick.
The hash is FNV-1a 64 over the canonical byte stream of ADR 0008 (format version 1).

`math-kernels` hashes one stream per tick, `STQK` header (format version, tick, seed and the hash of the previous tick) then the sections `DETM`, `ORBT` and `INTP` (tick 0 has `EDGE` instead), and the tick's hash is the checkpoint value, so a checkpoint covers every earlier tick.
It writes `f64` results as bit patterns, and a result that is a `Result` or an `Option` as a tag byte and the value or an error code.
A NaN result fails the scenario with exit status 2 (ADR 0008 treats a NaN as an error), so the inputs are chosen inside each function's domain.
The sign of a zero result of `min`, `max` and `clamp` is not part of an `f64` hash (`-0.0` is written as `+0.0`), so tick 0 writes it as a separate byte.
`data-fixtures` ignores `--checkpoint-every` (it has one tick), and its dump is one `DSET` line holding the 32 bytes of the data-set hash.
The fixture files are the ones `st-data` tests; the schema the harness loads them with mirrors the test schema, and a unit test pins the content hashes to the golden values in `crates/st-data/tests/golden.rs`.

The harness package is `tools/determinism`.
The expected output is `tools/determinism/reference.txt`.
It is generated on Linux, kept LF-only by `.gitattributes`, and read by a test with `include_str!`.

== Run it

Everything below runs inside `nix develop`, which provides the pinned toolchain and wasmtime.
Use your build slot as `CARGO_TARGET_DIR` as described in xref:adr/0004-build-resources.adoc[ADR 0004].

Run the harness and compare `[ci-tested]`:

[source,sh]
----
cargo run --release --locked -p determinism -- --out determinism-linux-x86_64.txt
diff -u tools/determinism/reference.txt determinism-linux-x86_64.txt
----

Options: `--scenario <name>` runs one scenario, and `--checkpoint-every <n>` takes a hash every `n` ticks to help find the tick where two platforms diverge (CI never changes it).
`--dump-tick <t> --dump <path>` also writes the canonical hash input at tick `t` (see <<_find_where_two_targets_diverge,below>>); the two options go together.
Exit status: 0 success, 1 usage or I/O error (including a `--dump-tick` past the end of every selected scenario), 2 a scenario failed (for example a `HashError`: a NaN in the state), 3 the leak detector saw a platform libm call outside its allow-list.

Run the tests, which include the same comparison:

[source,sh]
----
cargo test -p determinism -p st-sim -p st-rng -p st-data -p st-math -p st-time
----

== Run it on wasm32-wasip1

The dev shell sets `CARGO_TARGET_WASM32_WASIP1_RUNNER` to `wasmtime run --dir=.`.
The three commands below are `[ci-tested]`.
Outside the dev shell, set it yourself and install the target (`rust-toolchain.toml` already lists it).

[source,sh]
----
cargo test --locked --target wasm32-wasip1 -p st-math -p st-rng -p st-time -p st-sim -p st-data -p determinism
cargo run --release --locked --target wasm32-wasip1 -p determinism -- --out determinism-wasm32.txt
diff -u tools/determinism/reference.txt determinism-wasm32.txt
----

The first command runs the golden tests of `st-rng`, `st-data` and `st-math` and the `st-sim` tests under wasmtime.
It covers what ADR 0008 and ADR 0010 deferred until this harness existed.

== Change the reference on purpose

A change that alters simulation behaviour changes the hashes.
Regenerate the reference, review the diff, and say in the PR description why it changed:

[source,sh]
----
cargo run --release --locked -p determinism -- --out tools/determinism/reference.txt
git diff tools/determinism/reference.txt
----

A hash that differs on one platform only is a determinism bug, not a reason to regenerate.
Find where the platforms diverge as described next.

== Find where two targets diverge

The `determinism` job names the first diverging scenario and tick per target.
That tick is only a checkpoint, 120 ticks wide, so narrow it down and then look at the bytes:

[source,sh]
----
# 1. On both targets, one hash per tick; the first differing line is the tick.
cargo run --release --locked -p determinism -- --out fine.txt --scenario orbit-coast --checkpoint-every 1
# 2. On both targets, dump the canonical bytes at that tick (here 481) and diff the dumps.
cargo run --release --locked -p determinism -- --out fine.txt --scenario orbit-coast --dump-tick 481 --dump dump.txt
diff -u dump-linux.txt dump-other.txt
----

A dump line is `<scenario> <tick, 8 digits> <section> <id or -> <hex>`.
There is one line per section header (`STQH`, `ENTS`, `PILT`, `GLOB`, id `-`) and one per entity (`ENTS`, the ship id) or pilot (`PILT`, the pilot id).
The hex is the canonical byte stream of ADR 0008 for that line (format version 1), so concatenating the bytes of all lines of one scenario and hashing them with FNV-1a 64 gives the checkpoint hash (a test checks this).
The first differing line names the entity, and the first differing byte names the field: `f64` values are 8-byte little-endian bit patterns, written in the order of `Ship::state_hash_with_id` (`crates/st-sim/src/sim.rs`).
For `math-kernels` the lines are the sections `STQK`, `EDGE` (tick 0) or `DETM`, `ORBT` and `INTP`, with id `-`; the offset of the first differing byte in a section names the function, in the order of the code in `crates/st-sim/src/scenarios/kernels.rs`. For `data-fixtures` the one line is `DSET`.
Without `--scenario`, the dump has the lines of every scenario that reaches the tick.

== The leak detector

On x86_64 Linux only, the harness binary defines the C math symbols itself (`sin`, `cos`, `pow`, `log2`, `fma` and the rest listed in ADR 0008, with their `f`-suffixed versions).
Each definition counts its calls and forwards to the pure-Rust `libm` crate, so a call from any dependency into the platform libm is caught instead of silently using glibc.
After the scenarios the harness prints one line per symbol that was called, then a verdict, on standard output (an illustration of a failing run, not a real one):

----
leak-detector: log2 3 allowed (Parry's BVH, covered by the `parry_bvh_log2_domain` test)
leak-detector: cos 1 LEAK
leak-detector: FAIL, the platform libm was called (see LEAK lines)
----

A clean run prints `leak-detector: ok, no platform libm call outside the allow-list`.
Any symbol outside the allow-list (`log2`, `fma` and `fmaf` today, each with its reason in `tools/determinism/src/leak.rs`) makes the harness exit with status 3, after it has written the result file.
To test the exit-3 path, setting `DETERMINISM_LEAK_SELF_TEST` makes the run call the platform `cos` once; `tools/determinism/tests/cli.rs` uses it to check exit status 3 and the `LEAK` line.
The module is compiled into the binary only, on `cfg(all(target_os = "linux", target_arch = "x86_64"))`; tests and other platforms behave like the game and print nothing.
It is the one place in the workspace that allows `unsafe` (ADR 0008).
The simulation does not call the platform libm today, so the current allow-list is unused.

== In CI

[cols="2,3",options="header"]
|===
| Job | Step

| `test (linux-x86_64)`, `test (windows-x86_64)`, `test (macos-aarch64)`
| After `cargo test --workspace`: run the harness in release (on Linux with the leak detector), `diff` with the reference, upload `determinism-<platform>` (the upload runs even when the diff failed).

| `wasm32`
| Install wasmtime 49.0.2 (the nixpkgs version), run the tests on `wasm32-wasip1`, run the harness, `diff` with the reference, upload `determinism-wasm32`.

| `determinism`
| `needs` the four jobs above and runs with `if: ${{ !cancelled() }}`. Its first step fails unless every needed job succeeded. It then downloads the four artifacts, fails unless exactly those four files exist, compares each with `tools/determinism/reference.txt` and every pair with each other byte for byte, and prints the first diverging scenario and tick for each mismatch. It writes a summary table to the job summary.
|===

The artifacts are `determinism-linux-x86_64`, `determinism-windows-x86_64`, `determinism-macos-aarch64` and `determinism-wasm32` (ADR 0003), each holding `<artifact name>.txt`, kept for 7 days.
Download them from the run page to inspect a failure.

The comparison is `tools/ci/determinism-compare.sh <artifacts-dir> <reference-file>`; run it on a directory laid out like the downloaded artifacts to try it locally.
It exits 0 when all is equal, 1 on a mismatch or a missing or unexpected file.
The checks also reject a vacuous pass: the reference and every output must be non-empty, end with a newline, and have a line for each scenario of the reference, which must have at least five (`MIN_SCENARIOS` in the script, to be raised when scenarios are added).
An artifact directory with any file besides its own is rejected too.

A mismatch report looks like this (an illustration: the `wasm32` hash is the reference hash with its last character altered by hand):

----
MISMATCH: wasm32 differs from the reference
first difference at line 17 (scenario orbit-coast, tick 00000480)
    reference              orbit-coast 00000480 2c4aac5970b09a31
    wasm32                 orbit-coast 00000480 2c4aac5970b09a3X
    1 of 50 lines differ
----

The new job name is `determinism` `[ci-tested]`: it passed with four equal files in run 38130979625.
It is the tenth required check: it was added to branch protection (ADR 0003) after its first green run on `main`.
